# Settlo｜チーム共有：振り返りと今後の戦略

作成日: 2026-06-25 ／ 対象: チームメンバー全員
このドキュメントは、(1) SysHack の振り返り、(2) Geek Hack に向けた改善、(3) PayPay 等との差別化、(4) Vue+Firebase でアプリ化できるかの技術判断、(5) これまでの修正（治療）まとめ、(6) ファイル構造の整理 をまとめたものです。
※ 内容はすべて、実際のコード（`src/`・`functions/`・`firestore.rules` 等）を確認した上での記述です。憶測の箇所はその旨を明記しています。

## 0. 3行サマリー
- **動くものはできた。が「チーム開発」ではなく「1人実装＋AI」になっていた**のが最大の課題。次は“非コーダーが load-bearing（無いと困る）な役割”を持つ体制にする。
- **技術スタック（Vue3 + Firebase）はアプリ化に十分通用する**。ただし本番化の前提として **Firestoreルールの厳格化が最優先ブロッカー**（今は「ログインすれば誰でも全データ読み書き可」）。
- **差別化は「支払いの追跡・承認・催促・最小精算という“割り勘の台帳＋社会的ナビ”レイヤー」**。PayPayは送金、Settloはその上の管理。ここを一点突破でプレゼンする。

## 1. SysHack の振り返り（いけなかった点 / どうまとめるべきだったか）

### 1-1. 観測された問題（コードから事実として言えること）
| 観点 | 何が起きたか | 根本原因 |
|---|---|---|
| セキュリティ | APIキー・`service-account.json` を public リポジトリにコミット → 後から Git 履歴全書き換え | 秘密情報の扱いルールが無い／`.gitignore` 未整備／レビュー無し |
| 体制 | 1人（大崎）がコード＋AIをほぼ全部担当（本人も「作業しすぎた」と認識） | 役割分担がスキルに紐づいていない／コードを書けるのが実質1人 |
| 一貫性 | 配色バラバラ（緑/青/グラデ）・絵文字多用・フォント混在・データモデルの解釈ゆれ | 着手前に「共通ルール（デザイン/命名/データ）」を決めていない |
| 完成度の錯覚 | 招待・立替候補・精算内訳などが**ハードコードのモック**のまま“動いて見える” | 「完成 = 実データに繋がり、エラーも処理できる」の定義が無い |
| 壊れやすさ | イベント作成不能（テストルール期限切れ）・`indexOf`クラッシュ・フリーズ | テスト・エラーハンドリングの習慣が無い |
| 設計の迷走 | Express+TS バックエンドで始めて、途中で直Firestoreへ移行 → 残骸が放置 | アーキテクチャを最初に1つに決め切れていない |
| 再現性 | `firestore.rules` がリポジトリに無く Console 側のみ → 期限切れに気づけない | Infrastructure as Code（設定もコード管理）が無い・CI無し |

### 1-2. どうチームをまとめるべきだったか
- **役割を“スキル×成果物”で割る。ただし非コーダーにも load-bearing な担当を渡す。**
  - 例: コード2名 / デザイン1名（Figma で画面仕様＝正） / リサーチ・ユーザー検証1名 / PM・進行1名 / プレゼン・動画1名。
  - 「9人いるが非コード役割」だと“見ているだけ”になりがち。**デザイン仕様・ユーザーインタビュー・テストシナリオ・デモ台本・スライドは“無いと開発が進まない成果物”**にして全員に依存関係を持たせる。
- **初日に「決め」を3つ作る**: ①データモデル（後述の債権/債務）②デザイントークン（色・余白・コンポーネント）③運用ルール（秘密情報・コミット・ブランチ）。
- **コア設計を最初にペア/モブで合意**。Settlo は `transaction` の「誰が借りていて誰が貸しているか」が何度も誤解の元になった。ここを最初に紙で握れば後半の混乱の大半は消えた。
- **小さく頻繁に統合（feature ブランチ → レビュー → merge）**。1本の巨大な個人ブランチに溜めない（取り込みコスト・属人化・バス係数1の温床）。
- **「動いた」の定義を共有**: 実データ接続 + 主要エラー処理 + 空/読み込み状態まで。デモ用モックは“仮”と明記。

### 1-3. 今後の進め方（プロセス提案）
- **軽いが本物のプロセス**: GitHub Issues か簡易ボードで TODO 可視化 / feature ブランチ / merge 前レビュー（1人でも自己レビュー＋AIレビュー）。
- **リード3役**: テックリード・デザインリード・PM/プレゼンリード。意思決定の責任を分散。
- **大崎の働き方の調整**（重要）: 抱えすぎない。**「他人が拾える粒度の仕様」を書いて渡す**、ソロ作業はタイムボックス、他人の貢献を“本流に載る”ものにする。＝今回の「勝手にやりすぎた」を構造的に防ぐ。
- **秘密情報**: `.env` + Secret 管理を最初から。鍵はコミットしない。GitHub Push Protection は有効化済み（維持）。

## 2. Geek Hack に向けた改善

> 注: Geek Hack の審査基準そのものは未確認のため、以下は一般的なハッカソン審査（課題設定・実装・デザイン・プレゼン）で効く打ち手を Settlo 向けに具体化したもの。

### 2-1. プレゼン
- **課題ファースト**: 「割り勘した後、“誰がいくら返してないか”が曖昧で言い出しにくい」という具体的な痛みから入る。
- **差別化を1分の実演で見せる**: 支払い → **承認リクエスト** → 相手が承認 → 完了、と **催促 → 通知** の往復。「PayPayは送れる。でも“返ってきたか・催促したか”は管理できない」を実機で。
- **数字と物語**: 想定ユーザー（学生・サークル・旅行）、1イベントの平均人数・回数。可能なら小さなユーザーテストの声を1つ。

### 2-2. 説明動画
- **60〜90秒・ハッピーパスのみ**・字幕必須（音無し再生対策）。
- 構成: 問題(10s) → 解決の核(承認＆催促の往復, 30s) → 体験の気持ちよさ(20s) → 締め(ビジョン, 10s)。
- 画面録画は**実データ**で（seed スクリプトで安定状態を作ってから撮る）。

### 2-3. アプリのデザイン
- 既に **PayPay風リデザイン**（ブランド緑・フラット・絵文字廃止・SVGアイコン・モバイルシェル）は完了。次の磨き:
  - **空状態・ローディング（スケルトン）**の整備（“読み込み中…”を上質に）。
  - **余白・タップ領域・コントラスト**のアクセシビリティ確認（44px以上のタップ、AA コントラスト）。
  - **アプリアイコン・スプラッシュ・OG画像**（共有時の見栄え）。
  - **マイクロインタラクション**（完了時の小さなアニメ等）で“ちゃんとしてる感”。

### 2-4. これから加えていく要素（実装候補・優先度順）
1. **Firestoreルールの厳格化**（セキュリティ＝機能。後述）。
2. **本物のプッシュ通知**（FCM。`firebase.js` に messaging 初期化あり・受信導線を整える）。
3. **最小送金精算の表面化**（`functions/calculateSettlement` 実装済み。「3人の貸し借りを最小回数で精算」をUIで見せる＝強い差別化）。
4. **レシートOCR割り勘**（`functions/analyzeReceipt` = Gemini 実装済み。撮る→品目→自動割り勘）。
5. **プロフィール画像**（Firebase Storage 連携、現状TODO）。
6. **PWA化**（インストール可能・ホーム追加。後述）。
7. LINE 共有・ディープリンク等。

### 2-5. 自分（チーム/AI）が直したものを語れるように
プレゼンや技術質疑で「初期版から何を直したか」は加点になる。要点は §4 の治療まとめを参照。特に「**公開リポの鍵漏えいを検知して全履歴を書き換え・無効化**」「**支払いライフサイクル（承認・催促）を実データで実装**」「**1件の不正データで一覧全体が落ちるバグの発見と防御**」は“課題を見つけて直せるチーム”の証拠になる。

## 3. PayPay 等との差別化（割り勘アプリとして）

### 3-1. PayPay/LINE Pay 割り勘の限界
- **その場・同一ウォレット前提**の即時送金。全員が同じウォレットに入っている必要。
- **横断的な台帳が無い**: 「複数イベントをまたいで、誰が誰にトータルいくら」が残らない。
- **承認・催促のライフサイクルが無い**: 送ったら終わり。「本当に返ってきたか」「催促したか」は管理外。
- **イベント単位の品目割り勘・最小精算が弱い**。

### 3-2. Settlo の立ち位置（＝“送金の上に乗る管理レイヤー”）
- **関係×イベントの台帳**: 友だち単位・イベント単位で貸し借りを蓄積。
- **支払いライフサイクル**: `unpaid → 承認待ち(awaiting_approval) → 完了(completed)`。**双方が確認するまで“精算済み”にならない**＝言った言わない問題を解消。
- **催促（リマインド）＋通知**: 誰に何回催促したかを記録、再送時は確認。
- **最小送金精算 / OCR割り勘**（Functions 実装済み、表面化が課題）。
- **ウォレット非依存**: PayPayリンクを共有するだけ・現金も扱える（“支払った/受け取った”を人が確定）。

### 3-3. ポジショニングの注意
- 「PayPay を置き換える」とは言わない。**送金レール（PayPay等）の上に乗る「記録・精算・社会的ナビ」レイヤー**として位置づけるのが正直で強い。

## 4. これまでの修正（治療）まとめ

### 4-A. セキュリティ・基盤
- 公開リポの **鍵漏えい対応**: Gemini鍵×7・`service-account.json`×3 を履歴から除去（`git filter-repo`＋force push）、鍵は**全て無効化済み**。GitHub Secret Scanning + Push Protection 有効化。
- **`firestore.rules` をリポジトリ管理下に**して本番デプロイ（テストモード期限切れによる全書き込み拒否＝イベント作成不能を解消）。PR #104。
- ローカル開発: `.env.dev` を Vite が読まない問題 → `.env.local` で解消。

### 4-B. UI 全面リデザイン
- PayPay風・モバイルファースト・ブランド緑統一・**絵文字全廃（SVG化）**・和欧フォント統一。
- デザイントークン（`base.css`）＋共通クラス（`main.css`）＋共通ヘッダー/アイコン部品。
- 各画面の「角丸バナーがスクロールでずれる」崩れバグを `PageHeader` 統一で根治。

### 4-C. 実データ連携・ロジック
- **`transactions` を正データ化**。残高・履歴・サマリーを実データから導出。
- **支払いライフサイクル**を実装（unpaid→承認待ち→完了）。「完了でない＝未決済」を全ビューで統一し realtime 同期。
- イベント削除（取引・履歴・本体）/ 招待コード参加 / お支払い履歴の堅牢化（2クエリ・名前キャッシュ）。

### 4-D. 直近セッションの修正
- **承認フローの可視化を3箇所に**（お知らせ・お支払い精算のバッジ・詳細バナー）。
- **拒否フロー**（受取側が拒否→未払いに戻し相手へ通知→再リクエスト可）。
- **二重送信ガード**（連打でのエラー防止）＋ エラー時はモーダル表示。
- **重大バグ: `indexOf` クラッシュの発見と防御** — `paidToId` 欠落の不正取引が1件混ざると `getDoc(undefined)` で例外→**未払い一覧が丸ごと描画されず ¥0/0件**になっていた。原因を Console から特定し、相手UIDが無い取引をスキップするガードを追加。診断/掃除コマンド（`tx` / `cleanbad`）も整備。
- **催促機能の本実装**: 取引に `remindCount`/`lastRemindedAt` を記録、入金待ちに「催促 N回」表示、**2回目以降は再送確認**、相手へ実通知。お知らせは新着順・種類別（承認/拒否/催促）・「確認」で既読化。

## 5. アプリ化の技術判断（今の Vue + Firebase で大丈夫か）

### 結論: **十分いける。ただし“本番アプリ”にする前の必須課題がある。**

### 5-1. アプリ化の道筋（2択）
- **PWA（最短・推奨の第一歩）**: manifest + Service Worker を追加 → インストール可能なWebアプリに。プッシュは FCM。今の Vite SPA からの差分は小さい。
- **Capacitor（ストア配信が必要なら）**: 同じ Vue ビルドを iOS/Android シェルに包む。Firebase はそのまま流用。ネイティブのプッシュ/カメラが必要ならこちら。

### 5-2. 本番化の前提（優先度順の必須課題）
1. **【最優先】Firestoreルールの厳格化**: 現状は `allow read, write: if request.auth != null;` ＝**ログインすれば誰でも全ユーザーのデータを読み書き可**。これは個人情報・金額が見える割り勘アプリとして重大な穴。コレクション単位で「本人 / 取引当事者 / イベント参加者のみ」に絞る必要あり。
2. **ルーティングを hash → history に**（`/#/payment` → `/payment`）。Hosting の rewrite は設定済みなので移行可能。見栄え・共有リンクのため。
3. **バンドル分割**: 本番JSが単一 ~600KB。`manualChunks` 等で分割し初期表示を軽く。
4. **レガシーの撤去**（混乱の元）: 旧 Express+TS バックエンド（`server.js` / `src/index.ts` / `src/routes/*` / `src/middleware/auth.ts` / `src/logic/settlement.ts` / `settle.cjs` 等）は直Firestore移行で実質不要。※削除は要合意なので**提案に留める**。
5. **エラー/ローディング/オフライン**の整備（モバイルは電波が不安定）。
6. **クエリ設計**: 今は複合インデックス回避のためクライアント側JSフィルタ（＝全件読み→絞り込み）。データ増で**読み取りコスト・速度**が問題化するため、複合インデックス＋サーバ側クエリへ。
7. **データ整合性**: 今回の「相手ID欠落の不正取引」を生んだ作成経路（イベント分割など）を特定し、生成時バリデーションを入れる。

### 5-3. スケール観点
- 想定規模（学生コミュニティの割り勘）なら **Firebase の無料〜従量で十分**。Functions（OCR/精算）も onCall でOK。
- 将来の懸念は「全件読み→JS絞り込み」の読み取り課金とルールの緩さ。ここを直せば長く使える。
